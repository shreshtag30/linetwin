How LineTwin works — read this first

This is a live simulation of a 30-station vehicle assembly line (12 body stations, 6 paint stations, 12 final-assembly stations), running right now in a real Python process on the server — nothing on this page is pre-recorded. Every number updates 8 times a second as the simulated line actually runs.

Four real mechanisms are running underneath what you see:

  • Bottleneck detection — the Active Period Method watches which station has been continuously busy the longest, and names it the current bottleneck (§ Bottleneck card).
  • Defect-risk scoring — a trained model scores every station's risk of producing a defect right now, from live queue pressure and cycle-time signals (§ station tiles' risk values, if a model is trained).
  • Sensor-gap inference — 8 of the 30 stations have no sensor. Their values are estimated from neighboring stations by solving a graph equation live, and tagged inferred with an honest confidence percentage, never shown as if measured (§ station tiles' "inferred — N%" pills).
  • Rolling-horizon prediction — every second, the server forks the current state of the line and fast-forwards it ~30 simulated minutes to forecast where the bottleneck is headed next (§ Plant Manager tab's "Predicted downtime").

A fifth mechanism — defect genealogy, tracing a flagged defect backward to its likely origin station — is built and tested (src/twin/diagnostic/genealogy.py) but is not wired into this live dashboard; it runs against the event log on demand, not per tick.

Try this: go to the Perturbation panel below, pick any station and a cycle-time multiplier, and click Apply. Watch the Bottleneck card, the charts, and the Alerts feed respond within a couple of seconds — an explanation of exactly what should happen (and later, what actually did) appears right there.

Live alerts

How this works

Computed client-side from the same stream every other panel reads — nothing extra runs server-side for this. Three kinds of alert, each labelled with how sure it is, on purpose: the brief itself warns that false alarms erode trust, so every alert here says why and how confident, never just a bare red flag.

  • Bottleneck shift — the live detector's verdict changed station. Tagged provisional or established, exactly like the Bottleneck card.
  • Risk flag — a station's defect-risk score crossed the trained model's own tuned decision threshold (the same one it was evaluated against — not an arbitrary round number). Only fires once per rising edge, not every tick it stays elevated.
  • Sustained disruption — a station has been BLOCKED or STARVED for many consecutive ticks in a row, which usually means it's the real, ongoing effect of a slowdown elsewhere, not a one-tick blip.

Bottleneck

How this works

The Active Period Method: every station tracks how long it has been continuously "active" (working, or stopped for a reason that isn't its own fault — down, in repair, mid-setup). Whichever station's current active streak is the longest right now is the bottleneck. This exact method was benchmarked against 5 alternatives on this same line and won (100% top-1 accuracy against ground truth computed from a separate sensitivity analysis).

Confidence: "provisional" means the gap over the runner-up isn't yet large enough to call statistically clear; "established" means it is. This is shown as a caveat, not hidden — and deliberately never used to suppress an alert outright, since that would also slow down detection.

Perturbation

How this works

This is the one control that actually changes the live simulation: it multiplies one station's cycle time going forward (a value already mid-cycle finishes at its original speed — a real machine wouldn't jump speed mid-part either). Everything else on this page is read-only, watching the effect ripple through.

Line trend

How this works

Throughput (UPH) — units per hour the whole line is completing right now, averaged across all 30 stations' own completion rates. A slowdown at one station drags this down even if the other 29 are unaffected, because they end up starved or blocked waiting on it.

WIP (work in progress) — total units currently sitting in buffers between stations, summed across the whole line. Rising WIP is the earliest visible sign of a new bottleneck: units are piling up somewhere faster than they're draining.

Predicted downtime

How this works

Once a second, the server takes a copy of the line's current state (which stations are busy/blocked/starved, current queue levels, any perturbation you've applied) and fast-forwards that copy ~30 simulated minutes using an independent random sequence — a "what happens if things keep going like this" projection, not a claim of exactly replaying the real future. The forecast is then re-diagnosed the same way the live bottleneck is.

Distinct from the current bottleneck above — when they disagree, a shift may be coming.
